              2.4.7 Brake Resistor Interface
       The upper two solder pads in the 5-pin interface shown are the brake resistor interface. These are 2mm pitch pin holes, allowing
users to solder a 2mm straight single-row header. See Section 2.4.4.

       When configured as the brake interface, the driver continuously supplies a current to this interface upon power-up to keep the
brake open, enabling normal motor operation. If the driver loses power, this current ceases, locking the brake and immobilizing the
motor at the power-off position.

       When configured as a brake resistor interface, an external brake resistor (also known as a discharge resistor) can be connected.
When back EMF exceeds the threshold voltage, current is discharged through this resistor to prevent failure to emergency brake or
back EMF damage to the driver.




              2.4.8 Limit Switch Interface
       The driver provides two limit switch interfaces and supplies 12V power to external limit switches. The pin holes are spaced
2mm apart, allowing users to solder 2mm straight single-row pins. Refer to Section 2.4.4.

       LW1 is the minimum position limit switch, and LW2 is the maximum position limit switch. They can be connected to external
two-wire switches or three-wire NPN switches.

       1.       Set PID initial values


       2.       Set vel_integrator_gain to 0



            odrv0.axis0.controller.config.vel_integrator_gain=0


       3.      Adjusting the vel_gain method:


               1)       When rotating the motor in velocity control mode, if the rotation is unstable with jitter or vibration, decrease
                       vel_gain until the rotation stabilizes.


               2)       Then, increment vel_gain by approximately 30% each time until noticeable jitter occurs


               3)       At this point, reduce vel_gain by about 50% to achieve stability.


       4.       Adjusting pos_gain:


               1)       Rotate the motor in position mode. If rotation is unstable with jerking or vibration, decrease pos_gain until
                       rotation stabilizes.


               2)       Then, increment pos_gain by approximately 30% each time until position control exhibits noticeable overshoot
                       (i.e., the motor overshoots the target position and oscillates back to it).


               3)       Then gradually decrease pos_gain until overshoot disappears.


       5.       After completing these 4 adjustment steps, set vel_integrator_gain to 0.5*bandwidth*vel_gain, where bandwidth is the system
               control bandwidth.What is control bandwidth? For example, if the time from the user setting the target position to the
               motor actually reaching the target position is 10ms, then the control bandwidth is 100Hz. Thus, vel_integrator_gain =
               0.5 * 100 * vel_gain.

       In Position Control mode, the following are supported: Filtered Position Control, Trajectory Control (a type of position control), and

      Circular Position Control.

(Trajectory Control), and Circular Position Control.

       In velocity control mode, it supports direct velocity control and ramped velocity control;

      In torque control mode, both direct torque control and ramped torque control are supported.

       ⮚       Filtered Position Control

       If you wish to generate your own position curve and send position control commands at a specific frequency, use Filtered
Position Control. This mode smoothly connects and executes these commands. Using Trapezoidal Position Control in this scenario
may cause the motor to exhibit jerky or granular motion.

       In this mode, adjust the filter bandwidth based on the command transmission frequency. A good rule of thumb is to set the
bandwidth to half the command frequency (in Hz). For example, when sending commands at 50Hz:


           odrv0.axis0.controller.config.input_filter_bandwidth = 25

       Enable position control filtering:


           odrv0.axis0.controller.config.control_mode = 3

           odrv0.axis0.controller.config.input_mode = 3

       Then perform position control:


           odrv0.axis0.controller.input_pos = 10 # in turns



       ⮚       Trajectory Control

       This mode allows users to set acceleration, coasting speed, and deceleration to smoothly move the motor from one position to
another. The term "trapezoidal" refers to the speed curve resembling a trapezoid, as shown below where orange represents speed and
blue represents position:




                                                                       30
                             Jiangxi Sitawei Automation Equipment Co., Ltd.                                                          rev2.2

       Adjustable control parameters:

           odrv0.axis0.trap_traj.config.vel_limit # Maximum coasting speed, units: turn/s odrv0.axis0.trap_traj.config.accel_limit
           #Maximum acceleration, units: turn/s^2 odrv0.axis0.trap_traj.config.decel_limit # Maximum deceleration, units: turn/s^2
           odrv0.axis0.controller.config.inertia # Inertia, units: Nm/(turn/s^2)

       Note that inertia × acceleration = torque. This value defaults to 0. It can improve system response but is directly related to the
motor load.All four values above must be greater than or equal to 0. Additionally, note that previously mentioned current and speed
thresholds remain globally effective. For example, if the above coasting speed limit is set higher than the system-level vel_limit, the
global vel_limit takes precedence.

           odrv0.axis0.controller.config.control_mode = 3

           odrv0.axis0.controller.config.input_mode = 5

       Then perform position control:


           odrv0.axis0.controller.input_pos = 10 # in turns



       ⮚         Circular Position Control

       This mode is suitable for continuous incremental position control, such as when a robot hub rotates continuously in one
direction for a period or a conveyor belt runs continuously. If standard position control mode is used, the target position will gradually
increase to a very large value, potentially causing positioning errors due to floating-point precision issues.

       Enable:

           odrv0.axis0.controller.config.circular_setpoints = 1

       In this mode, each incremental step remains within a single revolution, with input_pos ranging from [0, 1). If input_pos exceeds this
range, it is converted to a value within a single revolution. To enable steps exceeding one revolution, set the following parameter to a
value greater than 1:

           odrv0.axis0.controller.config.circular_setpoint_range = <N>

      ⮚        By adjusting the maximum reverse current


           odrv0.config.max_regen_current = xxx # Maximum reverse current, positive value

      ⮚        By adjusting the back-EMF voltage range


            odrv0.config.enable_dc_bus_overvoltage_ramp = True odrv0.config.dc_bus_overvoltage_ramp_start = xxx #

       Note that both modes can be enabled simultaneously; the driver will attempt to combine both methods for discharge.

4       Communication Protocol and Examples

       4.1        CAN Simple Protocol
       The default communication interface is CAN, with a maximum communication rate of 1Mbps (readable and configurable via
odrv0.can.config.baud_rate). The default baud rate is 500Kbps. Note: In early hardware versions (≤3.7), USB and CAN are
incompatible. Refer to Section 3.1.8, Item 3) for instructions on switching from USB to CAN.

       The default protocol for the driver is CAN Simple. If the user switches to the CANOpen protocol, they must revert to CAN Simple
using the following command:


           odrv0.can.config.protocol = 1

       Note that on hardware versions 3.10 and above, the communication interface simultaneously supports RS485, pulse
direction, and PWM. Use the following command to ensure the communication interface is CAN:


           odrv0.config.comm_intf_mux = 0

       In Motor Genius, you can also switch the physical interface and CAN protocol version in the communication parameters.


                4.1.1 Protocol Frame Format
       CAN communication uses a standard frame format: data frame with an 11-bit ID and 8 bytes of data, as shown in the table
below (left: MSB, right: LSB):


  Data Field                                            CAN ID (11 bits)                                    Data (8 bytes)

  Segmentation        Bit 10 ~ Bit 5                         Bit4 ~ Bit0                                    Byte0 ~ Byte7

  Description        node_id                                  cmd_id                                        Communication Data



       ⚫        node_id: Represents the unique ID of this motor on the bus. It can be read and set in odrivetool
                using odrv0.axis0.config.can.node_id.

       ⚫        cmd_id: Command code indicating the message type in the protocol. See the remainder of this section for details.




                                                                       42
                            Jiangxi Sitawei Automation Equipment Co., Ltd.                                                             rev2.2
       ⚫      Communication Data: 8 bytes. Each parameter carried in a message is encoded as an integer or floating-point number in
              little-endian byte order. Floating-point numbers are encoded according to the IEEE 754 standard (encoding can be
              tested via https://www.h-schmidt.net/FloatConverter/IEEE754.html).

       Taking the Set_Input_Pos message described in 4.1.2 as an example, assume its three parameters are: Input_Pos=3.14, Vel_FF=1000
(representing 1 rev/s), and Torque_FF=5000 (representing 5 Nm). Given that the Set_Input_Pos message has a CMD ID=0x00C and the
driver's node ID (node_id) is set to 0x05, then:

       ⚫      The 11-bit CAN ID = (0x05 << 5) + 0x0C = 0xAC

       ⚫      According to the description of Set_Input_Pos in Section 4.1.2, Input_Pos occupies the first 4 bytes starting from byte 0,
              encoded as C3 F5 48 40 (the floating-point number 3.14 is encoded as a 32-bit IEEE 754 standard number

              0x4048f5c3), Vel_FF occupies the 2 bytes starting from the 4th byte, encoded as E8 03

              (1000=0x03E8), and Torque_FF occupies the 2 bytes starting from the 6th byte, encoded as 88 13

              (5000=0x1388). Thus, the 8-byte communication data is:


  Byte0            Byte1             Byte2             Byte3              Byte4            Byte5             Byte6             Byte7

  C3               F5                48                40                 E8               03                88                13

        4.2       CANOpen Protocol
        CANOpen is a communication protocol specification for the automation field. This product implements the CiA301, CiA302, and

               4.2.3 Frame Message
         Frame message formats vary depending on the CAN ID (COB-ID).


                      4.2.3.1     NMT (Network Management)
         NMT is used to broadcast status change commands to all nodes on the bus or to specific nodes. Its COB-ID is always 0, and
the data consists of 2 bytes, as shown in the table below:

  COB-ID                                         Data Byte 0                                   Data Byte 1

  0x000                                          Status Command Word                           node_id

         The status command word contains:

  Status Command Word                                                    Description

  0x01                                                                   Status changes to "operational"

  0x02                                                                   Status changes to "stopped"

  0x80                                                                   Status changed to "pre-operational"

  0x81                                                                   Reset node

  0x82                                                                   Reset communication

         For example, after connecting a drive, the user first sends the following NMT command to activate all nodes on the bus:

  COB-ID                                                                 Data

  0x000                                                                  01 00




                      4.2.3.2     SYNC
         The synchronization function synchronizes all nodes on the bus, primarily ensuring nodes synchronize PDO messages. Its
COB-ID is fixed at 0x80, with an empty data field.

      For example, after using the NMT command to activate nodes on the bus, users typically send a SYNC message to initiate PDO
data transmission.


                      4.2.3.3     PDO
         PDO is a communication method designed for real-time data transmission. It is used when users wish to periodically acquire node
data or when users need to report data in an event-driven manner. PDO is only used when the node status is "operational," so users must
first change the node status using an NMT message.

EDS file.

      4.5         Pulse/Direction Control
       Ensure hardware version is 3.10 or higher before using this feature, as it conflicts with the limit switch function. This is the simplest
method to control the driver, but also the most primitive and fragile. Therefore, avoid using this control method unless absolutely
necessary.

       This function supports controlling brushless motors via the traditional Step/Dir (pulse/direction) interface, enabling
compatibility with standard stepper motor drivers. In this mode:

       Step (pulse) signal: Each rising edge corresponds to the motor moving one preset step

       Dir (Direction) signal: Level determines movement direction (High level: clockwise / Low level: counterclockwise)

        // Pump events for 150ms. This delay is needed for two reasons;
        // 1. If an error condition occurs, such as missing DC power, the ODrive may
        //        briefly attempt to enter CLOSED_LOOP_CONTROL state, so we cannot rely
        //        on the first heartbeat response, so we want to receive at least two
        //        heartbeats (default interval 100ms).
        // 2. If the bus is congested, the setState command won't get through
        //        immediately but may be delayed. for (int i = 0;
        i < 15; ++i) {
             delay(10); pumpEvents(can_intf);
        }
    }



    Serial.println("ODrive running!");
}
